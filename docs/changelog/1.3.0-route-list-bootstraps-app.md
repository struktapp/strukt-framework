# route:ls lists the routes of a generated application

## What changed

`route:ls` previously read the shared router registry directly without ever
bootstrapping the application, so it always reported `No routes registered.`
even after `app:reload` produced a loader. It now performs the same bootstrap
as the generated front controller:

1. Registers the runtime autoloader (`Autoload::register`).
2. Builds the application from the generated `App\Loader` when one
   (with a `getApp()` method) is available, falling back to
   `Application::make()`.
3. Initialises the application so its module routes land on the shared router.

## Why

With `app:reload` restoring the loader and `app:exec` serving the app, the
developer-facing expectation is that a working app also introspects
(`route:ls`). Listing routes without registering the modules could never
reflect the application's actual routing table.

## Documentation

- None; `route:ls` usage is unchanged.

## Tests

- `tests/Unit/RouteListTest.php` added: lists the routes of a generated
  application, and prints the notice when no routes are registered.
- `tests/Unit/AutoloadTest.php`: the lib-class fixture now uses `App\Lib`
  instead of `App\Loader` so it cannot shadow the generated loader across
  tests in the same process.

## Public API impact

- None. `RouteList::execute()` signature is unchanged.
